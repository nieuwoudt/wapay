Pay Agent Architecture

The chat feels like a menu because the customer is talking to the pre-agent runtime: 29 deterministic intercepts, two serial classifier calls, and a model that has never been shown a single fact about the customer. The agent described in the recon was never built. This page shows what runs today, the target that six read-only readers, four independent designers, three judges and two refuters per claim converged on, and the order to build it in.

Architecture or implementation?

The plan on paper is right. The runtime is the old one.

When this page was first written (16 September, morning) only Phase 0 and 0.5 of the recon had shipped; the context pack, the registry and the tool-using loop had not started, and what the founder was reviewing was regex and templates with a two-tier classifier behind them. By the same night Phases 0, 1 and 2 were in production: the record and both sides of memory reach every turn, every surface renders from the registry, and the one-loop Pay agent runs for numbers on the shadow list. The intercept layer is still there for everyone else; Phase 3 removes it group by group with the eval as the gate.

Where we disagree

One brain, many hands. Not a main agent talking to specialist agents.

The founder's picture is right about ownership (each product owns its truth, tools and flow) and wrong about inference. Every extra model on a WhatsApp turn costs one to three seconds, a second prompt to keep truthful, and a second place to be wrong. The current two-tier engine already is "an orchestrator talking to category agents", and it is the thing being complained about. Specialists become modules, tools and off-path workers; one model composes.

What the moat is

Not the model, and not the number of agents. FNB already runs eWallet on WhatsApp, and any bank can rent the same model. The defensible asset is the per-customer record under one WhatsApp identity: every deposit, send, purchase, pay-out and pay link across every product, read on every turn, plus a policy-gated registry that any partner product (a bank link, a credit check, an insurance quote) plugs into as a module. That is what a bank cannot bolt onto a menu quickly, and it is the cheaper thing to build. So the order is plumbing first, brain second.

Where we are

Phase 2 is deployed behind the pilot list and THE PILOT WEEK IS RUNNING. It started on 19 September with 18 real agent turns, the first this build has ever had. Latest code 0deb5b7.

What the first day of it found, on the founder's own phone. Airtime could not be bought at all: the slot parser reads a bare 0787051175 as both a phone number and R787,051,175.00, and the guard meant to keep the amount he had already chosen compared digit-string prefixes and had silently stopped working for any number typed in the normal 0-form, so the preview rejected every attempt with "Amount must be between R5 and R1000". Answering "mine" cancelled the purchase outright, because it carries no digits and the not-a-phone-number branch reads that as an exit. Both are fixed (BUGLOG #76): the chosen amount now simply wins, which needs no heuristic, and one generous self matcher runs first.

And two true answers about his own money were being thrown away. "What do you know about me" and "a breakdown of my spend for last month" both came back as the fallback line, and the agent_turns rows show both firing the RECEIPT gate, which is one of the three the promotion week is measured on, so each false positive also reset the clean-day clock to zero. The provenance guard only ever knew the context pack, although the design has always said a figure may come from the record OR a tool result this turn; and zero was in no set, so an honest "completed spending total: R0" read as an invented figure. Fixed (BUGLOG #77): tool figures are merged in as quotable, never settled, so a success claim still has to name money the ledger says settled.

Memory changed direction on 19 September, on the founder's instruction: remember as much as possible from every interaction, unless the customer says not to. The confirmation turn added the day before is gone. The bigger fault found while removing it: the string notes did not occur once in lib/context-pack.js, so everything ever remembered had been written and never shown to the model. Notes are now in the customer record every turn. Three distinct controls: "stop remembering" refuses future writes and destroys nothing, "what do you know about me" shows everything, "forget me" erases.

Complete for every customer (Phases 0 and 1): the customer record and the last 12 turns, both sides, in every model turn; all five execute routes proving ownership before the PIN with the internal-auth gate failing closed; strict PIN states; claim release and the typing indicator; the INIT pay-out reconcile; registry-rendered surfaces; habits, memory and erasure; nightly balance integrity; the policy engine before proposals and withdrawals.

Phase 3, everything that does not need the gate, is now DONE. The source-text surgery that blocked moving anything out of the processor is at zero, from nineteen sites on 18 September. And "delete the regex layer with the eval as the gate" has become a mechanism: the eval did not exercise pay links, fuel, the product-browse hook or the category-context hook at all, so deleting those four would have proved nothing. Ten cases were added and tests/phase3-deletion-readiness.test.mjs now holds the deletion list itself, refusing any hook that has neither a covering case nor a recorded reason it is blocked. Running it found three wrong expectations of mine and one real limit: fuel is a founder pilot, so the registry keeps start_fuel out of the tool list and the agent explains instead of proposing, which means the fuel hook cannot be deleted until fuel goes live.

Phase 4 is mostly waiting on decisions rather than on code. The daily pay-out sweep now reports the backlog it could not reach, which is the number that decides whether the ten-minute schedule is still optional. Moving the sweep, retention and the integrity check into the jobs queue was deliberately NOT done: the drain runs inside the same daily cron that already runs them inline, so it would add a layer and buy nothing until a ten-minute drain exists.

Phase 3 preparation is DONE, which is why four rows turned green. The three dead things are deleted (a second WhatsApp client, the bypassing ledger writer postBluDeposit, a Prisma model for a table that never existed), and the first batch of source-text test locks is rewritten as behaviour: thirteen functions exported from the processor in place, surgery down from 19 sites to 6. Two tests were found to have been asserting against fakes that had drifted from the real code.

Phase 3 gate: the eval half is MET (156 cases, eleven languages, 100% on action). The week half is RUNNING and its clock is at zero, reset by the two false-positive gates on 19 September. It restarts on the next agent turn.

One row is amber on purpose. C11's policy engine has nothing configured that can refuse anything, and a consent requirement would be a tautology that does not address the cross-user risk it appears to; the reasoning is section 11 of the record.

"A main agent that talks to specialist agents"

The picture the founder described, drawn honestly next to the recommendation. The difference is where the specialists run, not whether they exist.

Products specialist

A read tool over the catalogue and embeddings, plus one proposal tool per product. Its knowledge block is attached to the prompt only when the capability is live for this customer and in focus.

Pay-outs specialist

The context pack carries the pending pay-out; a status tool asks the rail live; the reconcile sweep runs off-path every ten minutes and writes what it told the customer into the same history the agent reads.

Memory specialist

A query, not a model. The pack, the transactions tool and a curated customer record. A second model reading the same rows can only paraphrase them or invent, and the numeric-provenance guard exists precisely so numbers come from rows.

Sending money as easily as a text

Today "send" mints a voucher. In the target, the send proposal resolves the recipient from the record (a saved name, a shared contact card, or a number) and the registry picks the rail by who the recipient is: a WaPay customer gets a balance transfer, anyone else gets a voucher today and a pay-out once cash-out is open. The model names the person and the amount; it never chooses the rail. "Send R50 to mom" works from a saved name, and the confirm, PIN and receipt stay exactly as they are.

How "gets to know me over time" works

Three memory tiers, each with a named writer and a named reader. The model reads all three and may propose exactly one kind of write: a customer-stated note. Money facts are never written by the model.

  • Status questions ("did my payment go through") become a composition over the pack's recent movements: the newest candidate is named with its reference and state, and a second candidate is offered when two happened in the last day. Spelling and "to tbh" stop mattering because the candidate set comes from rows and the words only rank it.
  • Disambiguation and follow-up questions fall out of the same block: the model sees the R50 PayShap and the R20 deposit side by side and asks which one. Clarify is a first-class outcome, not a slot ask: the question and the pending intent are stored in flow state, and the next turn's answer is routed back to the agent with that intent in the record ("R50 airtime: for you, or for the number ending 4421 you usually buy for?").
  • Things the customer tells it ("I always buy for my mother", "call me Sipho") become notes through a propose_note tool: the runtime stores a note only when it contains no digits and is a direct statement about the customer, otherwise it asks once to confirm. The standing rule that the model writes no customer facts stays true; the feature ships in Phase 2.
  • Habits (usual airtime number and amount, the meter, the deposit rail, who gets sent money) are computed in SQL from the same tables, not remembered by the model, so "the usual?" is exact.
  • Retention and erasure become one delete on the turns table; the ledger and events stay as financial records. "What do you know about me" and "forget that" are ordinary tools.

The enterprise spine

"Robust and enterprise" here means fewer moving parts with more instrumentation, not more agents. Six deterministic components carry it.

Policy engine

Sits between a proposal and a flow start: allow, deny, or require a KYC tier, a consent version, a PIN or a limit. Reads per-capability policy blocks and the existing Consent and Limit tables. This is where counsel-approved wording for credit, insurance and bank linking lives, and it keeps them dark until cleared.

Output guards

Receipt shape, numeric provenance scoped to what matters (a balance, a status or a total stated as fact must come from the record or a tool result; limits, fee examples and echoed amounts pass), bearer digits, the partner and betting lexicon, message length. Totals over many rows come from the transactions tool's server-side sums, never from model arithmetic. A blocked reply degrades to a fact-built line, never to silence and never to "didn't catch that".

Audit trail

One append-only turn table with a JSON payload per message: prompt hash, tools called, proposal, policy decision, guard blocks, latency and cost. Proposals that reach a preview also go to the existing AuditLog keyed by the WhatsApp message id, so message to proposal to preview to idemKey to ledger entry is one query. A nightly job re-derives every wallet balance from the journal and raises drift in Mission Control.

Delivery and degraded mode

The webhook claims the message as in-flight and releases the claim on failure, with outbound sends idempotent per message id, so a killed turn is retried instead of silently lost. A typing indicator is sent before any work starts. A per-customer budget of model calls per hour stops a bored customer burning tokens. When the model is down, the guard list and the record still answer balance, status, help and the open flow deterministically; a second model provider is a later item, not a Phase 2 claim. Tool results and customer text are data in the prompt, never instructions.

Async jobs

One jobs table drained on a schedule: the pay-out reconcile sweep, the customer summary, retention, and every future slow job (a credit check, insurance quotes). Workers message the customer back through one helper that picks in-window text, direct send or a template, and writes into the same history the agent reads.

Evals

The golden corpus re-run through the agent with the pack and tools, scoring action, reply shape, language, latency and cost; the chat harness rewritten from exact copy to shape-and-fact assertions. English plus two languages first, the rest as promotion proceeds, and the translator kept as a fallback for the low-resource languages until their eval passes. Promotion per language is gated on both. Model ids stay env-tunable; "model-agnostic" is claimed only after a second provider has run the corpus.

Where the recommendation disagrees with the brief

  • "A main Pay agent that talks to specialist agents." No, not as separate model calls. The two-tier engine already is an orchestrator talking to category agents, and it is the source of the slow, fact-free answers. Specialists become tools, knowledge modules and off-path workers; one model composes per turn. Your mental model survives as the brain's tool list.
  • "A specialist for the customer's memory of transactions and pay-outs." Memory is a query and a read model, not a model. A model reading the ledger can only paraphrase it or invent, and the standing rule that the AI never states balances or statuses from its own head is enforced mechanically by the provenance guard.
  • "Streaming the answers like ChatGPT." WhatsApp delivers whole messages and cannot edit them. The ceiling is a typing indicator within half a second, one composed message in two to four seconds, and reply buttons for choices. From 1 October 2026 every extra in-window message is billable, so a stream of short bubbles is a cost, not a feature.
  • "Empowered by all sources of information." Not raw access to everything. A curated, redacted record and read tools; every number spoken must trace to the record or a tool result this turn; confirm, PIN and receipt copy stay templates and the model never sees a PIN turn. A hallucinated "your payment went through" is a fraud vector, so some answers stay deterministic by design.
  • "Gets to know me over time" does not mean the model remembers freely. Habits are computed from the ledger, notes come only from what the customer stated with provenance, and a number-free summary is a later option that lands together with a change to the standing rule in the code and the constitution.
  • "Super robust and enterprise" means fewer moving parts with an audit trail, evals and gates: one loop, typed tools, a policy engine, a turn ledger, deterministic money flows and a jobs table. Not more agents, not a platform, not MCP on the hot path. The processor gets smaller.
  • Insurance, credit checks and bank linking are counsel-first. Recommending insurance is FAIS intermediary activity, a credit enquiry needs NCA-grade consent and purpose, bank linking runs on an aggregator's terms with a sponsor bank. The registry and policy engine keep them dark and make them a module when cleared. Nothing here is permission to ship them or promise them in copy.
  • "Not running the orchestration agent right" puts the fault in the wrong place. The architecture in the recon is right and unbuilt; the running implementation is its opposite. The first visible improvement (ledger facts in AI answers, one withdrawal truth, a typing indicator) comes from plumbing in Phase 0, before any new brain exists.
  • "Like ChatGPT or Claude" should not mean open-ended chat inside a money product. Every off-topic turn costs a model call and a Meta message and adds risk. The persona stays warm and stays on the customer's money and the life around it; it declines the rest in one line.
  • The calendar. The work is about twenty-four working days of Claude sessions, but with one founder reviewing, deploying and testing on his own phone, that is six to eight calendar weeks. The founder-visible milestone stays early: ledger-aware answers in the first week, his own number on the new brain in the second or third.

How this was checked

Six read-only readers mapped routing, the brain, memory, the money boundary, the truth surfaces and the channel at the current build with file and line evidence. Four designers proposed independently from different angles (one brain, orchestrator plus specialists, memory first, financial platform). Three judges (founder, engineer, risk) scored all four on eight criteria; all three chose the one-brain design and grafted the same items from the others. One synthesis produced the recommendation; each of its twelve load-bearing claims was then attacked by two refuters, one against the code and one against Meta, Vercel and regulatory facts. Seven claims stood, four were corrected in wording, and one was refuted outright and changed the design (the events read model). A completeness critic then read the founder's message sentence by sentence against the result; its additions are on this page (the clarify outcome, the two-bubble rule, server-side totals, the note path, degraded mode, the moat, the send rail rule, the narrower provenance guard, fewer tables, and the calendar).
