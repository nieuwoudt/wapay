# WaPay — MVP Build Plan & Integration Knowledge Base (v1.2)

## Recommended choices (unchanged)

- **API runtime**: Vercel serverless (Node) with Vercel Cron; fallback retries via Supabase cron if needed.
- **Yoyo gift behavior (MVP)**: Auto‑issue on first deposit and auto‑top‑up on every deposit, behind a feature flag.

## Tech stack confirmation

- **Language**: TypeScript (strict), Node 20 LTS
- **Runtime**: Fastify (API/BFF), pnpm monorepo
- **DB/ORM**: Supabase Postgres 15 + Prisma; amounts as integer cents; UTC
- **Infra**: Vercel (serverless functions, env, cron)
- **Queues/Jobs**: Vercel Cron for retries/recon; optional Supabase cron jobs
- **Auth & Sessions**: WhatsApp wa_id + device/session binding; PIN with Argon2id (+ pepper)
- **Validation**: Zod for input/response schemas; typed provider clients
- **Logging/Obs**: pino (JSON), Sentry, Vercel log drain → Axiom/Logtail; correlation by idem key
- **Security**: Idempotency on money mutations; redaction of voucher PINs; least‑privilege secrets in env
- **Testing**: Vitest, Supertest; Insomnia collection for manual E2E
- **CI**: GitHub Actions (lint, typecheck, build, prisma migrate diff)

## MCP tools to enable

- **Vercel** (deployments, env vars, projects, cron jobs, log drains)
- **Supabase** (Postgres admin, SQL console, migrations, cron)
- **Sentry** (DSN/project mgmt, releases)
- **Axiom or Logtail** (log ingestion from Vercel)
- **Meta WhatsApp Cloud API** (app, templates, webhook verify)
- **Blu Voucher** (QA/Prod, Swagger/OpenAPI)
- **Blu VAS** (QA/Prod)
- **Yoyo/wiGroup** (CVS/VSP)
- **Pay@** (SFTP, presentment; Phase 3)
- Optional: **openapi-typescript/orval** for typed clients

## WhatsApp (Meta) — channel & templates

- Inbound: webhook (`X-Hub-Signature-256`) → router → user session state machine
- Outbound: Utility templates only for transactional flows
- Template governance: static text around vars, `R {{2}}` spacing, samples match, no header/footer vars for MVP, punctuation, minimal/no emojis
- Minimal templates: `redeem_in_progress`, `deposit_receipt`, `deposit_failed`, `topup_collect_number`, `airtime_select_amount`, `airtime_preview_confirm`, `airtime_receipt`, `data_select_bundle`, `data_preview_confirm`, `data_receipt`

## 2.4 Conversational NLP / Chat Banking Layer (Phase 2)

Goal: Free‑form commands (e.g., “buy me R50 Vodacom airtime”, “what’s my balance?”, “top up Hollywoodbets R100”) that still route through preview → PIN → execute and use Utility templates for confirmations/receipts.

Module layout

```
/packages/nlp
  nlp.entities.ts     # currency, amount, msisdn, network, operator, contact name
  nlp.parser.ts       # deterministic parsing: regex + phrase tables; normalizes to Intent
  nlp.intents.ts      # intent schemas + validators (zod)
  nlp.router.ts       # maps Intent → BFF API calls (preview/execute)
```

Supported intents (v1)

- `check_balance`, `buy_airtime`, `buy_data`, `betting_topup` (Phase 2 flag), `p2p_send` (Phase 3 flag)

Entity extraction (deterministic)

- Amounts: `R50`, `50 rand`, `R 50.00` → `amount_cents: 5000`
- Networks: Vodacom|MTN|Cell C|Telkom → `VODA|MTN|CELL|TELK`
- Operators: Hollywoodbets, Betway, Lottostar → `operator_code`
- Targets: `+2782…`, `082…` → `target_msisdn`
- Bundles: `1gb`, `500mb`, `daily`, `weekly`, `30-day` → `{ size_mb, validity_days }`

Normalized Intent schema

```json
{ "intent": "buy_airtime|buy_data|betting_topup|check_balance|p2p_send", "amount_cents": 0, "network_code": "", "operator_code": "", "target_msisdn": "", "bundle": { "size_mb": 0, "validity_days": 0 }, "note": "" }
```

Conversation policy

- NLP triggers on inbound free text in an active session
- Always confirm via Utility templates; if missing entities, do one disambiguation step (quick replies)
- Always route preview → (PIN if needed) → execute

Telemetry & safety

- Log `{intent, entities, confidence, corrections}`; rate‑limit NLP; reuse same `idem_key` within 60s

## User Stories (MVP + Phase 2 NLP)

- Deposit via Blu Voucher
  - As a user, I redeem a Blu voucher PIN and see my wallet credited with a receipt.
  - Acceptance: `POST /deposit/blu/redeem` with idempotency; ledger balanced; WhatsApp receipt.

- Check wallet and gift balances
  - As a user, I ask "what’s my balance?" and receive wallet and gift (Yoyo) balances.
  - Acceptance: one Utility template with both balances and a reference.

- Buy airtime (NLP or menu)
  - As a user, I say "buy me R50 Vodacom airtime for 082…".
  - Acceptance: network inferred or disambiguated once; preview → confirm → (PIN) → receipt.

- Buy data (NLP or menu)
  - As a user, I say "buy 1gb weekly for 082…".
  - Acceptance: bundle resolved; preview → confirm → (PIN) → receipt.

- Betting top‑up (Phase 2, lightweight)
  - As a user, I say "top up Hollywoodbets R100".
  - Acceptance: operator supported; show instructions or voucher submit; send receipt on confirm.

- Retailer eligibility (Yoyo)
  - As a user, I ask "Can I use WaPay at Checkers?".
  - Acceptance: `GET /yoyo/eligible?retailer=checkers` returns supported true/false; bot replies accordingly.

- Pay at retailer with wiCode (Yoyo)
  - As a user, I say "I want to pay R79.88 at Checkers"; I receive a wiCode to present at POS.
  - Acceptance: if eligible, `POST /yoyo/token/issue` returns `{ token, type: 'WICODE' }`; confirmations and advice handled via VSP Request→Advice.

- Disambiguation and safety (NLP)
  - As a user, if my command is incomplete, I’m asked one concise follow‑up (amount, network, contact).
  - Acceptance: exactly one disambiguation step; replays reuse the same `idem_key` within 60s.

## Security & compliance

- PIN: Argon2id + pepper, attempt rate‑limits; gates on stale sessions/thresholds
- PII: store msisdn/wa_id/display only; never store voucher PINs
- Idempotency: mandatory header; store/short‑circuit duplicates
- Redaction: mask voucher PINs; avoid payload logging
- Access: least privilege; rotate creds; separate QA/Prod

## Observability & SLOs

- Correlate by `idem_key` across logs/provider calls
- Metrics: success %, p95 latency, 4xx/5xx, replay ratio, SLA breaches
- Dashboards: per‑provider tiles; error class drill‑down; alerts

- “buy airtime” → prompt for amount + number
- “R20 recharge Vodacom” → prompt for number
- “send 100 to Thandi” → prompt for which Thandi if multiple

### Negative/Blocked

- Marketing/emoji-heavy commands → respond with neutral prompt; handle via structured flows
- Unrecognized operators → ask once; on failure, offer supported list
